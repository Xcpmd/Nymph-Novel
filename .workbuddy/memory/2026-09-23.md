### 废案：后端早已完整，缺的是接线

### 修复废案序号撞车的既有缺陷

- 原实现把原位置编码进 `index_no`：`-(100000 + 原序号)`。同一卷里若有两个章节先后从同一位置被废，算出的负数完全相同，会被 `UNIQUE(volume_id, index_no)` 挡下，**第二次设为废案直接失败**。
- 改为新增 `original_index_no` 列单独记录原位置，`index_no` 只负责唯一，冲突时继续往下找可用值。还原时优先读新列，读不到再退回旧编码规则。
- 加列无法写成幂等语句，因此给迁移结构加了 `run` 钩子：先查 `PRAGMA table_info` 判断列是否存在，不存在才 `ALTER TABLE ADD COLUMN`。这是为迁移增加「需要程序判断」能力的第一处用例。

- 界面：条目上显示「启用版本号/总版本数」，编辑弹窗里列出版本历史并可切换启用。

## 工作台流程调整与章节操作修正

用户反馈若干问题：手写方向不该跳过大纲这一步；②要能按段提要求改大纲；②应产出章节目录；正文生成失败的提示不知所云；正文疑似被覆盖；章节序号该填整数。

### 手写方向回到第二步

- 之前按用户要求做成「手写方向直接建成事件、跳过第二步」，现在改回：手写与 AI 方向走同一条路径，都进入「检视并修改故事大纲」。手写内容直接建事件会绕开大纲，后续推进就缺了骨架。
- 相应地删掉 `createManualEvent` 与手写专用提示文案。

### 大纲其实发送了，但「生成失败」是真问题

- 用户从日志判断「只发了要求没发大纲」。实查那条 `outline_revise` 请求，user 段第 29 行就是「当前事件大纲：」加完整大纲，**大纲确实发出去了**，可能是只看开头没往下翻。
- 真正的问题在另一处：模型不按约定输出步骤区块时，服务端直接判失败，界面只显示「大纲缺少步骤清单」，用户手上的大纲白生成了。
- 改为退一步用 `deriveStepsFromOutline` 从大纲结构推导推进步骤，有序列表、小节标题、自然段都能落成步骤；确实推不出才失败，且错误信息说清了原因与对策。事件下发时带 `stepsDerived` 标记。

### 按大纲拆分章节

- `story-events` 的 updateItem 新增 `action: 'splitChapters'`：把事件的每个推进步骤建成一章，回填 `eventId` 与 `stepIndex`。
- 已经建过的步骤跳过，重复点击不会产生重复章节。
- 界面上是第二步里的一个明确按钮，而不是自动执行——自动建章会一口气产生大量空章节，交给用户点一下更稳妥。

### 章节序号改为整数输入，并补上移动能力

- 新建章节表单把「章节标题」的必填取消，改为「章节序号」数字输入；标题留空时按序号自动命名，用户不必手写「第一章」这类汉字。
- `updateChapter` 原本不支持改序号，因此新增 `moveChapterToIndex`：目标位置及其后章节顺移一位，序号先全部落到负数占位再写回正数，以避开 `UNIQUE(volume_id, index_no)`。

### 修掉批量移动章节文件互相覆盖的缺陷

- 调整序号或重编号时，原先按顺序逐个改名。排在后面的章节常常正占着前面章节的目标路径，直接改过去会互相覆盖，在 Windows 上直接报错，结果是文件与序号对不上。
- 改为先把所有要动的文件挪到卷目录下的临时名，再统一落到目标位置。`renumberChapters` 与 `moveChapterToIndex` 共用 `relocateChapterFiles`。
- 这个缺陷之前一直存在，只是重编号时较少触发；这次做序号移动才暴露出来。

### 接口返回结构调整

- 章节更新的返回值由裸 chapter 对象改为 `{ chapter, chapters }`，与新建、废案、还原等分支保持一致。前端只调用后刷新，未依赖旧结构，冒烟脚本的断言同步更新。

- 拆分与序号实测十三项全通过：按步骤建出三章、标题取自步骤、步骤序号回填、重复拆分不产生重复章、移动后顺序正确且序号连续、正文文件随序号改名。

## 修复方向变量未填充，并把格式问题降级为提示

### 手写方向其实一直没被送达模型

- 用户反馈手写大纲后进第二步，生成时用不上。查日志发现那条 `outline` 请求里「已确认的故事方向」是空的，而用户手写的内容出现在「用户补充要求」下面。
- 根因：模板里写的是 `{{direction}}`，但服务端构建 `vars` 时**从未提供 `direction`**。之前为了让它能出现在提示词里，把 direction 拼进了 `instruction`，于是内容显示在错误的一栏，模板里专门指认方向的那一行始终空白。
- 修复：`vars` 补上 `direction`，`instruction` 只保留额外要求，不再拼接。日志实测方向一栏已正确填充且不重复。

### 格式问题不再拦截

- 原先前一步已改为「没有步骤区块时从大纲文本推导」，但两者都拿不到时仍会判失败，整份大纲被丢弃。
- 现在彻底不拦截：大纲正文照常落库成事件，只发一条提示说明这一步暂时无法逐章推进，把决定权留给用户。事件页可以自行补步骤。
- 用无效模型名触发失败来验证变量填充（请求文本在此之前已落库，不消耗生成额度），另用 overrideSystem 要求模型只输出纯 Markdown 来验证格式容忍，两条路径都通过。

### 大纲不再出现在正文区

- 各步骤共用同一个生成钩子，第二步产出的大纲留在 `generation.text` 里，切到第三步时正文区会把它显示出来，字数统计也跟着算错。
- 按 `generation.meta.taskType` 区分：只有 `chapter` 与 `chapter_revise` 的输出才进正文区与字数统计，保存到章节也只写这部分。正文区为空时给一句说明。

### 本轮的坑

- 模板变量与 `vars` 的对应关系没有校验机制，漏掉一个变量只会静默变空。先前用「把值拼进另一个变量」代偿，反而掩盖了缺失，让内容出现在错误的段落里。**改提示词或改 vars 时，两边要一起核对。**

## 页面草稿缓存与步骤自选

### 切页不再丢失未保存内容

- 客户端路由切换会卸载页面组件，普通 state 里的输入随之消失。新增 `useDraftState`：状态镜像到 localStorage，回到页面自动恢复。
- 三点设计取舍：key 必须带上小说 id，否则换一本书会读到上一本的内容；写入做防抖，正文编辑器每敲一个字都写一次会拖慢输入；提交成功后调 clear，否则下次进来又冒出旧内容。
- key 里再编入条目 id（章节 id、事件 id）就能做到一条草稿对应一个条目，切换条目天然不串。
- 加载数据时走 `hydrate`：有草稿以草稿为准，没有才用磁盘内容。直接 setValue 会把用户的未保存内容冲掉。
- 弹窗表单挂不了 hook，另做 `useFormDraft` 与直接读写的三个工具函数，用 effect 监听表单变化落草稿，避免逐个替换页面上已有的 onChange。
- 已接入的页面：工作台的四处输入、章节详情的正文与指令、事件页的大纲编辑与新建、章节与大纲的编辑弹窗、角色、百科、关系、时间轴。

### 两个真实缺陷

- **设定页卸载时会取消待执行的保存**。原先的清理函数只是 clearTimeout，用户在防抖窗口内切走页面，那一次改动就永远留在内存里 —— 表单上看不出异常，回来看却是旧值。改为卸载时立刻发出。
- 工作台的大纲草稿有同样问题，同样改为补发。补发要用到最新值，而清理函数只建立一次，捕获不到后续渲染的变量，因此用 ref 转一手。

### 本轮要写的步骤可自选

- 原先固定跟随事件进度，想回头补第 2 步或先写高潮那一步都做不到。现在 `buildContext` 接受 `stepIndex`，缺省仍是进度所在那一步。
- 界面上先是做成一排可点击的步骤按钮，随后按用户要求改为下拉菜单，用 `primitives` 里的 Select 而非原生 select。选项文案里标出「已完成」与「进度所在」，选中进度所在那一步等于回到跟随进度。
- **推进条件同步收紧**：只有写的正是进度所在那一步才推进事件。否则补写或跳写会把后面几步当成已完成跳过。
- 渲染步骤清单时把标记从「当前」改为「本次要写」，避免与事件进度混淆。

### 验证结果

- 步骤自选七项实测全通过：缺省落在第一步、指定第三步后焦点与「本章要写的步骤」一栏同步、前两步标为已完成、越界收敛到最后一步。
- `npm run typecheck`、`npm run lint` 无问题，一百八十五项测试通过，文案七百一十五键缺失零，冒烟八十项通过。

## 修废案时撞唯一约束

### 现象与根因

- 用户废案一章时报 `UNIQUE constraint failed: chapters.volume_id, chapters.index_no`，位置在 `renumberChapters` 写回正常章的序号那一步。
- 根因：**废案章的序号停在正数区**。本意是让废案章落到 `<= -100000` 的保留区，与正常章的正序号互不干涉；但用户数据里二十个废案章的序号是 1 到 20，正常章排在 21 之后。一废案触发重排，正常章要从 1 开始重编，正好压在废案章身上。
- 查证时先怀疑是查询没排除废案章，实际 `renumberChapters` 早已加了 `status != 'scrapped'`；**问题不在查什么，而在废案章本该待的地方没待住**。

### 修复

- `renumberChapters` 把同卷废案章一并纳入搬移：两组各自先挪进负数暂存区（分两段避免交叉），正常章落到 1..N，废案章落到负数保留区。
- 新增迁移 v11，按卷把停在正数区的废案章重新编号到保留区，处理已存在的历史数据。

### 数据修正与一个反复

- 用脚本直接对用户库执行了同一套修正，二十个废案章从 1..20 变成 -100020..-100001。
- **第一次修正后复查又变回正数**。原因是 WAL 未落盘，读到的仍是旧快照。补上 `wal_checkpoint(TRUNCATE)` 后序号稳定。教训是直接改库后要让改动真正落地，再谈验证。
- 修正后备份了小说目录与数据库，位置在 `data/.backup-*` 与 `data/.nymph-db-backup-*.db`。

### 顺带发现的既有数据问题

- 核对数据库与磁盘时发现用户这本小说的数据本身已不一致：数据库里有十个章节记录了字数，磁盘上却只有四个正文文件有内容，且这四章在库里的字数记为零。
- 这**不是本次操作造成的**，也不是本次报错的原因，但没有确凿依据的情况下不宜代为修复，因此只记录、不动手，交由用户在界面上核对。

### 验证结果

- 复现历史数据形态后实测十项全通过：废案不再报错、正常章从 1 连续、废案章全部落在负数保留区、两段序号不重叠、还原后序号无重复且都在正数区。
- `npm run typecheck`、`npm run lint` 无问题，一百八十五项测试通过，文案七百一十七键缺失零，冒烟八十项通过。
