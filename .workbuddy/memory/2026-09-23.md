# 2026-09-23 工作日志

## 百科条目改为多版本、废案接线、大纲的手动与 AI 修改

用户要求：事件大纲与故事大纲要有修改功能；章节目录里的删除改为「设为废案」，废案后才能彻底删除，废案移出正常目录，还原前需把当前占用者设为废案；百科新增同名条目时改为建新版本，只启用最新版本，AI 查询只发启用版本，可手动指定启用哪一版，默认启用 AI 最后添加的。

### 废案：后端早已完整，缺的是接线

- `scrapChapter`、`restoreChapter`、接口 `action: scrap/restore`、目录页的数据加载与三个操作函数都已存在，但**目录页完全没有渲染废案区**，卡片上的垃圾桶仍走直接删除，且引用的 `removeChapter` 根本没有定义——项目当时处在编译不过的状态。
- 补上：垃圾桶改为「设为废案」（图标换成归档箱），新增废案区面板，可展开查看、还原、彻底删除，并把缺失的文案补齐。

### 修复废案序号撞车的既有缺陷

- 原实现把原位置编码进 `index_no`：`-(100000 + 原序号)`。同一卷里若有两个章节先后从同一位置被废，算出的负数完全相同，会被 `UNIQUE(volume_id, index_no)` 挡下，**第二次设为废案直接失败**。
- 改为新增 `original_index_no` 列单独记录原位置，`index_no` 只负责唯一，冲突时继续往下找可用值。还原时优先读新列，读不到再退回旧编码规则。
- 加列无法写成幂等语句，因此给迁移结构加了 `run` 钩子：先查 `PRAGMA table_info` 判断列是否存在，不存在才 `ALTER TABLE ADD COLUMN`。这是为迁移增加「需要程序判断」能力的第一处用例。

### 百科条目与正文分离

- 新增 `encyclopedia_versions` 表。条目只承载名称、分类、别名这类身份信息，正文按版本保存。
- 同名条目再次登记时不建重复条目，而是追加版本并把旧的停用，默认启用最新一版。
- `listEncyclopedia` 与 `getEncyclopediaEntry` 返回的正文取启用版本，因此给模型的上下文自动只剩启用版本，检索与索引层无需改动。
- 手动编辑改的是当前启用版本，不会凭空多出版本；条目尚无版本时补一个。
- 版本来源记 `origin`，区分模型抽取与用户填写。
- 旧列不删：SQLite 的列删除无法写成幂等语句，改为清空以免与版本表并存两份内容。
- 界面：条目上显示「启用版本号/总版本数」，编辑弹窗里列出版本历史并可切换启用。

### 大纲的修改入口

- 事件大纲：事件页新增直接编辑大纲正文的弹窗。步骤清单默认不动——步骤上可能有用户调整过的时间与细节，重推会丢，因此「按新大纲重推步骤」做成开关，默认关闭。
- 整本书大纲：设定页的大纲总纲新增「用 AI 修改」，按指令改写，结果先展示再确认写入。
- 大纲节点：节点上新增 AI 撰写入口，依据整本书大纲与节点标题展开。节点信息经 instruction 拼装交给模型，没有为此扩展上下文变量表。

## 请求日志面板与上下文超预算的二次确认

用户要求：右下角加一个小按钮，点开可看向 AI 请求的日志，含发送的文本、AI 输出的文本、token 统计，失败时返回报错；上下文超出预算时不再裁剪，改为发送二次确认按钮。

### 请求日志

- `generation_runs` 表原先只有请求参数与输出，缺「实际发出去的消息」与「本次用量」。v10 迁移补 `prompt_text` 与 `usage_json` 两列，同样走 `run` 钩子先查表结构再加列。
- 发消息时把 `composed.messages` 拼成可读文本存进 `prompt_text`，形如「【system】…【user】…」，便于事后核对到底给了模型什么。
- 用量在流结束时随状态一并落库，失败时 `error` 已有记录，日志里直接展示。
- 新增 `generation-runs` 资源（列表与单条），供界面读取。
- 界面：右下角一枚圆钮，展开成面板，列出最近四十条记录；每条显示状态、任务类型、模型、token 与时间，展开可见用量明细、发送文本、返回文本与报错。
- 日志按小说归属，因此只在小说页面内显示。
- **日志按钮与 Toast 都在右下角，会重叠**。把 Toast 上移一档让位。

### 上下文超预算改为二次确认

- 原实现遇到某层超出限额就静默截断。现在 `buildContext` 增加 `allowTrim` 选项，默认仍裁剪；请求体新增 `confirmOverBudget`，为真时不再裁剪。
- 服务端在组装上下文后先判断：未确认而出现裁剪，就只回一条 `budget-exceeded` 事件，带上实际 token 总量、预算与超出的层，**不创建运行记录也不调用模型**；用户确认后重发同一请求，这次保留全文。
- 界面侧 `useGeneration` 新增 `budgetExceeded` 状态与 `confirmBudgetAndRetry`，后者用上次的请求参数加上确认标记重发。
- 确认条做成独立组件 `BudgetConfirmPrompt`，四个生成入口各放一处：工作台、章节详情、设定页的 AI 改大纲、大纲页的 AI 撰写。

### 验证结果

- 迁移实测：user_version 推到 10，`prompt_text` 与 `usage_json` 两列已建立。
- 超预算实测：把预算压到极小后发起生成，收到询问事件且**没有开始生成**，事件里给出 315 token 与两层超出明细；带确认标记重发则直接进入生成流程。
- 日志实测：一次失败请求在日志里留下了 1967 字的发送文本（含 system 与 user 段）、输出字段与接口报错。
- `npm run typecheck`、`npm run lint` 无问题，一百八十五项测试通过，文案六百七十一键缺失零，冒烟八十项通过。

## 工作台流程调整与章节操作修正

用户反馈若干问题：手写方向不该跳过大纲这一步；②要能按段提要求改大纲；②应产出章节目录；正文生成失败的提示不知所云；正文疑似被覆盖；章节序号该填整数。

### 手写方向回到第二步

- 之前按用户要求做成「手写方向直接建成事件、跳过第二步」，现在改回：手写与 AI 方向走同一条路径，都进入「检视并修改故事大纲」。手写内容直接建事件会绕开大纲，后续推进就缺了骨架。
- 相应地删掉 `createManualEvent` 与手写专用提示文案。

### 大纲其实发送了，但「生成失败」是真问题

- 用户从日志判断「只发了要求没发大纲」。实查那条 `outline_revise` 请求，user 段第 29 行就是「当前事件大纲：」加完整大纲，**大纲确实发出去了**，可能是只看开头没往下翻。
- 真正的问题在另一处：模型不按约定输出步骤区块时，服务端直接判失败，界面只显示「大纲缺少步骤清单」，用户手上的大纲白生成了。
- 改为退一步用 `deriveStepsFromOutline` 从大纲结构推导推进步骤，有序列表、小节标题、自然段都能落成步骤；确实推不出才失败，且错误信息说清了原因与对策。事件下发时带 `stepsDerived` 标记。

### 按大纲拆分章节

- `story-events` 的 updateItem 新增 `action: 'splitChapters'`：把事件的每个推进步骤建成一章，回填 `eventId` 与 `stepIndex`。
- 已经建过的步骤跳过，重复点击不会产生重复章节。
- 界面上是第二步里的一个明确按钮，而不是自动执行——自动建章会一口气产生大量空章节，交给用户点一下更稳妥。

### 章节序号改为整数输入，并补上移动能力

- 新建章节表单把「章节标题」的必填取消，改为「章节序号」数字输入；标题留空时按序号自动命名，用户不必手写「第一章」这类汉字。
- `updateChapter` 原本不支持改序号，因此新增 `moveChapterToIndex`：目标位置及其后章节顺移一位，序号先全部落到负数占位再写回正数，以避开 `UNIQUE(volume_id, index_no)`。

### 修掉批量移动章节文件互相覆盖的缺陷

- 调整序号或重编号时，原先按顺序逐个改名。排在后面的章节常常正占着前面章节的目标路径，直接改过去会互相覆盖，在 Windows 上直接报错，结果是文件与序号对不上。
- 改为先把所有要动的文件挪到卷目录下的临时名，再统一落到目标位置。`renumberChapters` 与 `moveChapterToIndex` 共用 `relocateChapterFiles`。
- 这个缺陷之前一直存在，只是重编号时较少触发；这次做序号移动才暴露出来。

### 接口返回结构调整

- 章节更新的返回值由裸 chapter 对象改为 `{ chapter, chapters }`，与新建、废案、还原等分支保持一致。前端只调用后刷新，未依赖旧结构，冒烟脚本的断言同步更新。

### 验证结果

- 拆分与序号实测十三项全通过：按步骤建出三章、标题取自步骤、步骤序号回填、重复拆分不产生重复章、移动后顺序正确且序号连续、正文文件随序号改名。
- `npm run typecheck`、`npm run lint` 无问题，一百八十五项测试通过，文案六百七十八键缺失零，冒烟八十项通过。
- 正文格式核查：用户两章正文均为标准 Markdown，空行分段，其中一章含 72 个发言标记；另一章没有标记是模型没按提示词输出，与保存格式无关。

## 修复方向变量未填充，并把格式问题降级为提示

### 手写方向其实一直没被送达模型

- 用户反馈手写大纲后进第二步，生成时用不上。查日志发现那条 `outline` 请求里「已确认的故事方向」是空的，而用户手写的内容出现在「用户补充要求」下面。
- 根因：模板里写的是 `{{direction}}`，但服务端构建 `vars` 时**从未提供 `direction`**。之前为了让它能出现在提示词里，把 direction 拼进了 `instruction`，于是内容显示在错误的一栏，模板里专门指认方向的那一行始终空白。
- 修复：`vars` 补上 `direction`，`instruction` 只保留额外要求，不再拼接。日志实测方向一栏已正确填充且不重复。

### 格式问题不再拦截

- 原先前一步已改为「没有步骤区块时从大纲文本推导」，但两者都拿不到时仍会判失败，整份大纲被丢弃。
- 现在彻底不拦截：大纲正文照常落库成事件，只发一条提示说明这一步暂时无法逐章推进，把决定权留给用户。事件页可以自行补步骤。
- 用无效模型名触发失败来验证变量填充（请求文本在此之前已落库，不消耗生成额度），另用 overrideSystem 要求模型只输出纯 Markdown 来验证格式容忍，两条路径都通过。

### 大纲不再出现在正文区

- 各步骤共用同一个生成钩子，第二步产出的大纲留在 `generation.text` 里，切到第三步时正文区会把它显示出来，字数统计也跟着算错。
- 按 `generation.meta.taskType` 区分：只有 `chapter` 与 `chapter_revise` 的输出才进正文区与字数统计，保存到章节也只写这部分。正文区为空时给一句说明。

### 本轮的坑

- 模板变量与 `vars` 的对应关系没有校验机制，漏掉一个变量只会静默变空。先前用「把值拼进另一个变量」代偿，反而掩盖了缺失，让内容出现在错误的段落里。**改提示词或改 vars 时，两边要一起核对。**
